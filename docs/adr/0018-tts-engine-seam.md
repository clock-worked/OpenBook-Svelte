# The TTS engine seam is a named interface, and the chunk plan knows its limits

Local TTS engines sit behind one named interface, `AudioEngine` (`py_services/chapter_audio/engine.py`): `generate_audio(text, sample_path, output_path, seed)` plus three declarations: `adapter` (the provider profile's adapter name, ADR 0015), `max_chunk_chars` (the longest text one call accepts, `None` for no limit) and `normalize(text)` (the text this engine hears; idempotent). `ChatterboxLocalService` (450 chars) and `VibeVoiceLocalService` (no limit) are its two adapters. This is consistent with ADR 0011: the engines stay separate integration adapters, and the seam only gets a name and a type. `chapter_audio_test/` is renamed `chapter_audio/` because the package is production core.

Three rules are binding:

1. **No engine re-chunks.** The chunk plan accounts for the engine's limit at plan time: `plan_engine_chunks` sub-splits the alignment chunks (≥ 800 chars, the pipeline/WhisperX granularity) into the engine's true chunks. Every entry is one `generate_audio` call and carries `chunkIndex` (1..N engine calls), `alignmentChunkIndex` and `subChunkIndex`/`subChunkCount`. The pipeline's `chunkIndex`/`chunkTotal` progress and the generation report's `chunkCount` count engine calls (`alignmentChunkCount` gives the parents). A single line is planned the same way (`generate_engine_text`). An engine handed text over its limit raises `EngineChunkTooLongError`, and `generate_line_chunked_chapter_audio` rejects an unsplit plan before it generates anything.
2. **Normalization is declared on the adapter.** The answer to "what text does this engine hear" is the adapter's `normalize`. Shared primitives live in `chapter_audio/text_utils` (`normalize_typography`, `normalize_chapter_text`, `split_text_to_max_chars`). Only cloud engines get the bare typography primitive (`AudioGenerationService._normalize_text`).
3. **Engine adapters are built at the composition root.** `AudioGenerationService.audio_engine(provider, …)` looks the adapter up through the provider profile (`LOCAL_ENGINE_CLASSES`) and returns a voice-bound `AudioEngine` (`audio/engine_adapters.py`). No pipeline defines its own adapter.

**Considered options**: let the engine keep re-chunking internally (progress would count the 800-char chunks while the engine made 450-char calls, and nothing would show it); one shared normalizer for every engine (the replacement sets differ for good reasons: VibeVoice needs its pause/abbreviation rules, Chatterbox does not). Accepted costs: the Chatterbox pipeline path now hears typography normalization, which it skipped before. VibeVoice now maps U+FFFD to an apostrophe. Chatterbox chunk files from earlier runs no longer line up with plan indices when resumed.
