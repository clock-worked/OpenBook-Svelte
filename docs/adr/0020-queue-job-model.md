# One queue job model: one type, one planner, one state machine

A queued audio job used to live in three places that had to agree: the `audioQueue` store item (in localStorage), a `queuedJobs` Map inside `AudioPanel.svelte` (lost on navigation), and a payload rebuilt from disk when the Map missed. The panel also had its own single-chapter planner beside `audioQueuePlanning.ts`. Now one module owns the job: `apps/desktop/src/lib/services/audioQueueJob.ts`. It defines the `QueueJob` type, the transitions (`applyQueueEvent`) and the persisted view (`serializeQueueState` / `restoreQueueState`). `stores/audioQueue.ts` is a thin persistent store that applies those transitions, and `audioQueuePlanning.ts` is the only planner.

Four rules are binding:

1. **One type everywhere.** A job has the same `QueueJob` shape in memory, in localStorage and after a restart. The in-memory `plan` (the lines, voice and character counts `generateAudioForCharacter` needs) is the only field that is not persisted. A restored job has `plan: null`, and `rebuildQueuedJobPayload` rebuilds it from the job's own `lineRefs` (chapter, line id, planned character). With the same disk state, the rebuilt plan equals the one the planner made. A line that has since been reattributed or that already has audio is dropped. The component keeps no copy of job state.
2. **The store owns the state machine.** The only changes are `enqueue`, `start`, `progress`, `finish(ok | fail | cancel)`, `cancel`, `remove`, `clearFinished`, plus the selector `next`. Illegal transitions are rejected and leave the queue unchanged: `start` works only on a queued job and only while no other job runs, `progress` only while running, `finish` only on an active job, `remove` only on a queued job. Restart recovery happens in `restoreQueueState`: a job that was running goes back to queued, or to canceled if a cancel was pending. A second runner, such as a remounted panel, gets `false` from `start` and backs off.
3. **One planner.** Every enqueue path (one character, whole chapter, whole book, advanced) builds its jobs through `audioQueuePlanning.ts`. The single-chapter path is `planChapterCharacter`, which shares `collectScriptCharacterLines` with the other planners. "Which lines are missing for a character in a chapter" has one implementation.
4. **Progress is true progress.** `progress.record` holds the latest `PipelineProgressRecord` from candidate 7 (ADR 0019). The overlay shows its phase and engine-chunk counters ("chunk 3/7"). `linesDone` counts only lines the pipeline has finished. Nothing converts chunks into line counts.

Tested through the interface: `__tests__/audioQueueJob.test.ts` covers the restart rebuild for single-chapter, whole-book, speaker-source and full jobs, every legal and illegal transition, and parity of `planChapterCharacter` with the old shadow planner. `stores/__tests__/audioQueue.test.ts` covers the store.

**Considered options**: persist the full plan in localStorage (whole-book jobs carry every line body and could hit the storage quota, and stale text would be generated after edits); keep the old rebuild that keys on character and chapter (a restored whole-book or speaker-source job shrank to one character in one chapter and lost its advanced options); move the runner loop out of the panel into the store (it depends on the panel's voice, name and script lookups, so that is left for later). Accepted costs: storage moves to `openbook.audioQueue.v2`. A v1 queue is read once, and its jobs, which have no line refs, use the legacy rebuild. Single-chapter lines are now stamped with chapter, source and character context like the other planners' lines, so `chosenSpeaker` is filled in when a line has none. The overall line bar still moves only when a job finishes, because the pipeline reports chunks, not lines.
