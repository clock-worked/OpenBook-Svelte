# Character stats have one answer

Extends ADR 0012. The backend's accumulated stats, written onto each character record (`stats.totalLines` / `stats.chapterCount`), are the one answer to "how many lines does this character have?". The frontend never re-derives book-wide stats from dialogue or scripts: `services/characterStats.ts` is the only reader (`characterStats`, `characterLineCount`, `characterChapterCount`), and every badge, sort and count goes through it. The legacy `count` / `chapterCount` mirrors are read there only as a fallback for records with no `stats` (ADR 0003), and are no longer written. Where a per-chapter view is needed, `chapterLineCounts` in the same module counts one chapter's already-loaded lines. Loading a book only backfills a missing `firstAppearance`; it does not write stats.

On the backend, one function (`stats_for_character` in `update_character_stats.py`) joins raw dialogue keys to character records (exact id, case-insensitive id, exact name, case-insensitive name), for both the v3 folder and the legacy file writer. `set_book_root`'s accumulation build is visible: the response reports `stats_rebuilt` and a failure is logged with its traceback. A build failure never fails the root switch; the delta path builds lazily.

**Considered options**: keep the four frontend derivations and make them agree (parity would have to be tested forever, and the load-time re-derivation kept writing character files beside the backend's writer); make the frontend the owner (FSA and sidecar modes would diverge, and ADR 0012 already put the accumulation on the backend). Accepted cost: opening a book no longer repairs stale stats from the dialogue; the full rebuild (`/api/update-character-stats`) is the repair.
